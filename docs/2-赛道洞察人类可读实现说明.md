# 政策与行业信号监测及赛道洞察：人类可读实现说明

## 一、整体流程

这套系统要做的事情，可以概括为：

```text
增量采集政策和行业信息
→ 解析、去重并提取产业事件
→ 匹配已有话题
→ 聚类发现新增话题
→ 对比历史识别变化
→ 归并并验证业务赛道
→ 评估区域和 SMB 经营价值
→ 发布赛道注册表及周期洞察
```

各步骤的本质和主要技术如下：

| 步骤 | 本质 | 主要技术 |
|---|---|---|
| 获取材料 | 从确定的信息入口持续发现新增政策和行业材料 | 网站采集、API、定时增量任务 |
| 解析材料 | 把网页和 PDF 转换成统一文本和元数据 | HTML/PDF 解析、文本清洗、文档版本管理 |
| 材料去重 | 识别转载、重复页面和内容更新 | 内容哈希、文本相似度、来源关联 |
| 提取事件 | 从长文章中提取“谁在什么地区做了什么” | 规则抽取、大模型结构化抽取、证据定位 |
| 合并事件 | 将同一现实事项的多次报道合并 | 实体、时间、动作和文本相似度匹配 |
| 匹配已有话题 | 判断新事件是否属于已经观察的产业主题 | 关键词词典、向量相似度 |
| 发现新增话题 | 从无法匹配的事件中寻找反复出现的新方向 | 文本向量、聚类、大模型命名 |
| 识别变化 | 判断话题是否新增、升温、回落或区域扩散 | 时间窗口统计、归一化、透明规则 |
| 形成候选赛道 | 把相关话题整理成可经营的企业集合 | 事件关联、产业链角色归并、大模型语义判断 |
| 验证正式赛道 | 检查信号、边界、企业集合和经营价值 | 规则校验、证据校验、大模型生成定义 |
| 评估区域 | 判断赛道的主要区域和热门区域 | 区域实体识别、区域信号统计、产业基础证据 |
| 评估 SMB 价值 | 将企业经营活动映射为可能的 IT 需求 | 通用 IT 分类、大模型生成映射、人工修订 |
| 发布结果 | 生成可持续使用的赛道定义和洞察 | 结构化数据、版本管理、自动报告 |

## 二、如何从材料中提取产业事件

这一环节不会只依赖规则，也不会把所有工作都交给大模型，而是采用“程序解析 + 规则提取明确字段 + 大模型理解语义 + 程序校验”的组合方式。

### 程序负责的内容

- 将网页和 PDF 转换成文本；
- 提取标题、发布时间、发布机构和文号；
- 识别明确的日期、金额、数量和地区名称；
- 保存原文位置，供后续生成证据引用；
- 检查大模型输出的数据结构和引用是否有效。

这些信息格式相对明确，用程序处理更稳定、便宜，也容易复查。

### 大模型负责的内容

- 判断一篇材料中包含几件不同的事情；
- 识别谁采取了什么行动、面向什么对象；
- 判断事件属于政策、申报、认定、项目还是采购；
- 理解政策措施、企业活动和产业概念；
- 从跨段落内容中整理事件关系；
- 为每个结论引用对应的原文片段。

例如，面对一篇地方政府工作报告，大模型输出的不是文章摘要，而是类似下面的结构：

```text
事件类型：项目进展
主体：某产业园区
动作：建设工业视觉设备生产基地
阶段：开工
地区：某市某区
产业概念：工业视觉、智能制造
证据：原文中的具体段落
```

### 为什么不只用规则

政策和行业材料的写法差异很大，同一件事可能使用完全不同的表达。仅靠关键词和正则表达式，容易漏掉隐含的主体、对象和动作，也很难处理一篇文章中的多个事件。

因此，POC 可以让大模型处理经过相关性筛选的有效材料。规则主要承担明确字段提取、前置筛选和结果校验，而不是承担全部语义理解。

## 三、哪些步骤使用大模型

需要大模型的步骤主要有五类：

1. **复杂事件提取**：从政策和行业材料中抽取主体、动作、对象、阶段和产业概念。
2. **新增话题整理**：为聚类结果命名，并生成话题定义和关键词。
3. **话题归并和拆分**：判断两个相似话题是否属于同一方向，或者一个过宽话题是否应当拆开。
4. **赛道形成**：生成候选赛道名称、定义、纳入条件、排除边界、企业活动和产业链角色。
5. **SMB 经营价值分析**：把企业经营活动映射为可能的 IT 需求，并生成可解释说明。

周期洞察中的文字解释也可以由大模型生成，但只能根据已经计算好的指标和已有证据进行总结。

以下工作不需要大模型：

- 网页下载和附件保存；
- HTML、PDF 基础解析；
- 内容哈希和精确去重；
- 时间窗口统计；
- 信号数量归一化；
- 来源健康检查；
- 状态规则计算；
- 版本管理和结果发布。

文本向量模型用于计算语义相似度和聚类，它属于模型能力，但不是负责生成文字结论的大语言模型。

## 四、是否需要自己写爬虫

需要，但不是为每个网站从头写一套完全独立的爬虫。

系统会先实现一套通用采集框架，负责：

- 定时运行；
- 下载网页和附件；
- 限速、重试和失败记录；
- 判断页面是否已经采集；
- 保存原始内容；
- 记录每个来源是否正常。

然后为不同网站编写少量配置或适配器，告诉通用框架：

- 从哪个栏目页发现文章；
- 如何找到下一页；
- 哪个位置是标题和发布时间；
- 如何找到正文和附件；
- 网站有哪些特殊规则。

结构简单的网站主要通过配置接入；结构特殊的网站才需要编写专用适配器。

## 五、爬虫是否只处理指定网站

稳定的数据主干只采集预先登记的网站。

这样才能知道：

- 我们计划覆盖哪些来源；
- 每个来源是否按时运行；
- 没有发现材料，还是网站采集失败；
- 不同时间段的信号是否可以比较。

如果完全依赖临时全网搜索，搜索结果和排序会不断变化，系统无法判断历史趋势，也无法说明自己到底覆盖了什么。

因此，指定网站持续采集是系统的基础。

## 六、是否需要全网搜索

需要搜索，但搜索只作为补充发现手段，不作为主要统计来源。

搜索主要用于：

- 发现指定网站之外的长尾政策和项目页面；
- 为新出现的话题寻找更多独立来源；
- 查找企业、园区和项目的补充证据；
- 发现值得加入来源注册表的新网站。

搜索得到的摘要不能直接计入信号。系统需要访问原始页面、保存材料、识别来源、完成去重并提取事件后，才能进入正式分析。

POC 第一阶段可以先以指定网站为主，暂不建设自动化全网搜索流程。需要补充证据时可以执行少量定向搜索。等主流程验证合理后，再把搜索服务接入为自动补漏通道。

系统不会建设一个无边界、持续遍历整个互联网的通用爬虫。

## 七、如何从大量事件中提取具体赛道

事件到赛道不是一次模型调用完成的，而是经过“事件特征化—话题聚类—候选赛道归并—四类门槛验证”四个阶段。

### 第一步：给每个事件增加可比较的特征

系统从事件中整理：

- 涉及的技术、产品和应用；
- 企业在做什么；
- 企业属于什么产业链角色；
- 事件属于政策、申报、项目还是采购；
- 发生在哪些地区；
- 事件的语义向量。

这些特征使不同写法的事件可以被放在一起比较。

### 第二步：形成 Topic

新事件先匹配已有 Topic。例如，与工业视觉、机器视觉检测相关的事件会优先进入已有“工业视觉”Topic。

无法匹配的事件进入聚类。如果多条独立事件反复提到相似的技术、企业活动或应用场景，就形成一个新 Topic。大模型负责给聚类结果起一个可理解的名称，并草拟定义。

Topic 表示“外部世界正在讨论和发生什么”，它可以比较宽，也可以暂时边界不清。

### 第三步：从 Topic 归并候选赛道

系统寻找具有共同企业经营活动、产业链角色和 IT 需求的 Topic。

例如，一批事件分别涉及：

- 地方发布机器视觉产业扶持政策；
- 园区建设视觉检测设备项目；
- 多家企业入选智能制造示范名单；
- 工厂采购视觉质检设备。

这些事件可能先形成“机器视觉”“智能质检”“视觉检测设备”等 Topic。系统进一步判断，它们是否共同指向一组从事工业视觉质检设备、软件和方案服务的企业。

如果成立，候选赛道应当是类似：

> 工业视觉质检设备及方案

而不是过宽的“人工智能”或“智能制造”。

### 第四步：通过四类门槛形成正式 Track

候选赛道必须同时满足：

- **信号成立**：不是单一事件或集中转载；
- **边界成立**：能够说明包含什么、不包含什么；
- **企业集合成立**：能够描述参与企业及产业链角色；
- **经营价值成立**：能够说明可能产生的标准化 IT 需求和 SMB 覆盖方式。

程序负责检查事件数量、来源数量、时间窗口和证据是否达标；大模型负责生成及判断语义边界、企业活动和 IT 需求映射。四项全部通过后，程序生成正式 Track。

## 八、最终得到什么

系统最终输出的不是一份没有结构的行业文章，而是：

- 当前观察的产业 Topic；
- 每个 Topic 的信号变化；
- 自动生成并验证的正式 Track；
- Track 的定义、纳入和排除边界；
- Track 中的企业活动和产业链角色；
- 主要区域和热门区域；
- 可能产生的 SMB IT 需求；
- 支持上述结论的事件和原始证据；
- 可以按周期比较的版本化赛道注册表和洞察结果。

整个过程的核心分工是：程序负责采集、整理、统计、校验和发布；向量模型负责相似度和聚类；大模型负责复杂语义理解、命名、边界和解释。
