# 政策与行业信号监测及赛道洞察系统方案 V0.1

## 一、项目定位

本项目面向联想 SMB 业务，建设可持续运行的政策与行业信号监测及赛道洞察系统。系统在明确的来源、区域和时间范围内持续采集政策、项目、产业和市场材料，识别相较历史基线新增、升温、降温或进入新阶段的产业方向，形成有证据、可解释、可版本化的赛道，并判断其是否具备联想 SMB 可经营的客户基础和 IT 产品或服务需求。

项目不是一次性行业报告生成器，也不是依靠 Agent 临时搜索少数案例的演示。第一阶段目标是在有限来源范围内形成完整、可重复、可扩展的工程闭环，并以覆盖率、变化检测能力、赛道质量、SMB 相关性、运行成本和可审计性验证可行性。

本项目是整体能力的第一部分。后续“库内客户赛道识别与标签化”项目通过版本化赛道注册表消费本项目结果，不与本项目共用采集和运行流程。

## 二、业务目标

系统需要稳定回答以下问题：

1. 指定区域近期新增了哪些与产业发展相关的政策、申报、名单、项目和市场事件；
2. 哪些主题相较前一周期或历史基线出现信号增长、区域扩散、政策升级或落地加速；
3. 分散信号是否共同指向一个边界清晰、可持续观察的赛道；
4. 赛道中是否存在足够的中小企业、区域集群和可批量识别的企业特征；
5. 赛道可能产生的 IT 需求是否标准化、可复制，并适合联想 SMB 销售或渠道体系覆盖；
6. 本期重点赛道相较上一期新增、消失、升温、降温或发生了什么阶段变化。

项目输出服务于赛道选择、库内客户圈选和后续差异化经营，不直接认定企业采购需求、CRM 商机或销售机会。

## 三、现有实践形成的设计约束

### 3.1 Agent 适合语义判断，不适合承担全量发现

开放网络搜索和大模型研究可以产出少量高质量案例，但搜索覆盖不可测、结果不稳定，且时间和 Token 成本随材料及企业数量增长。即使增加并发、队列、断点恢复和逐任务校验，也只能提高执行可靠性，不能改变逐对象调用模型的成本结构。

因此，全量采集、去重、过滤、统计和初步分类必须由程序、规则及可批量运行的算法承担。大模型只处理经过筛选和压缩的高价值候选。

### 3.2 持续变化必须建立在历史数据上

仅搜索“最近的政策和热点”只能发现当前材料，无法可靠判断相较以前的变化。系统必须持续保存原始文档、首次发现时间、发布时间、版本和主题指标，并至少使用近期窗口与历史基线进行比较。

### 3.3 政策热度、产业热度和 SMB 价值必须分别判断

政策发布不等于产业已经落地，产业升温也不等于适合 SMB 业务。系统分别保存政策信号、实施信号、市场信号和 SMB 适配判断，不用单条政策、单个重大项目或单家头部企业直接生成重点赛道。

### 3.4 发现与验证采用不同门槛

发现阶段以覆盖为目标，允许保留噪声和信息不完整的候选；验证阶段以证据、边界和业务可用性为目标。不得在上游使用过窄规则造成不可恢复的漏召，也不得为达到预设数量降低正式赛道门槛。

### 3.5 事实、推断和业务建议分层保存

- 事实由原始来源直接或部分支持；
- 推断引用已保存事实并标明不确定性；
- SMB 业务建议基于赛道特征和联想能力形成，不表述为已确认客户需求；
- 搜索摘要、模型复述、来源不明转载不能独立支持关键事实；
- 多篇转载同一原始事件只计算为一个独立信号。

### 3.6 模型结果必须经过确定性处理后入库

模型可能产生字段漂移、重复 ID、悬空引用、错误枚举和无证据结论。模型输出只能作为候选产物，需经过结构规范化、引用检查、证据检查和 Schema 校验后成为正式对象。

### 3.7 质量、覆盖和业务正确性分别评估

- 结构校验证明数据格式和引用关系有效；
- 覆盖审计证明计划来源、区域和信号类型得到处理；
- 业务评审判断赛道边界、变化解释和 SMB 价值是否合理。

三者不能相互替代。

### 3.8 局部失败不得阻断整期结果

单个网站失效、附件解析失败、模型任务失败或候选赛道需要复核时，应保留失败记录并继续处理其他对象。系统支持最小工作单元重试、断点恢复和带缺口交付，不因局部异常重跑全部数据。

## 四、总体技术路线

采用“自建核心来源库 + 搜索发现补漏 + 多源信号融合 + 分层算法处理 + 有限大模型判断”的混合路线。

```text
来源注册表
  ↓
定时增量采集
  ↓
原始文档与附件存储
  ↓
解析、标准化、去重与版本识别
  ↓
结构化事件和主题特征提取
  ↓
历史基线与近期变化检测
  ↓
已知主题匹配 + 未知主题发现
  ↓
候选赛道归并、验证和生命周期管理
  ↓
SMB 适配评估
  ↓
赛道注册表、周期洞察和质量报告
```

商业政策或产业数据源作为可选输入，通过统一适配器接入，不影响下游对象和算法。系统不依赖任何单一商业数据源，也不把自建采集器与业务判断耦合。

## 五、数据源策略

### 5.1 来源分层

#### 核心官方来源

- 国务院政策文件库；
- 国家发展改革委、工业和信息化部、科技部、财政部等重点部委；
- 目标省、市、区政府门户及发改、工信、科技、财政、中小企业主管部门；
- 中国政府采购网及地方公共资源交易、政府采购平台；
- 国家统计局及目标地区统计部门。

#### 产业落地来源

- 申报、试点、示范、认定和资金结果名单；
- 项目签约、开工、投产和扩建信息；
- 产业园区、开发区和产业集群官方信息；
- 行业协会、标准组织及权威研究机构；
- 企业官方公告和重大项目披露。

#### 市场补充来源

- 权威综合媒体和专业行业媒体；
- 融资机构及企业官方融资披露；
- 搜索服务发现的长尾页面；
- 其他可追溯到原始来源的聚合线索。

### 5.2 来源注册表

每个来源至少保存：

- 来源 ID、名称、发布机构和来源等级；
- 覆盖区域、行业和内容类型；
- 发现方式、入口 URL 和解析器；
- 抓取频率、限流和失败策略；
- 最近成功时间、连续失败次数和健康状态；
- 使用限制、证据用途和配置版本。

### 5.3 POC 覆盖原则

第一版不追求全国全网完整覆盖。应明确选择：

- 国家层面的核心政策入口和重点部委；
- 三个产业结构不同的代表性区域；
- 政策、申报、名单、项目、采购、统计和有限行业资讯七类信号；
- 至少十二个月历史回采，条件允许时回采二十四个月；
- 日级或周级增量采集，周级赛道更新。

系统必须发布来源覆盖清单和采集健康情况，不对未覆盖范围作完整性承诺。

## 六、核心数据模型

### 6.1 Source

描述一个可持续采集的来源及其覆盖、可信度、发现方式和运行状态。

### 6.2 Document 与 DocumentVersion

Document 表示一个稳定的逻辑文档，DocumentVersion 表示该文档在一次发布或内容变化后形成的具体版本。每次采集保留对应原始快照和内容哈希，后续解析及抽取结果引用明确的 DocumentVersion，不覆盖历史版本。至少保存：

- 标题、发布机构和文号；
- 发布时间、首次发现时间和抓取时间；
- 地域、正文、附件及内容类型；
- 原始 URL、父页面 URL、文件哈希和正文哈希；
- 来源等级、访问状态、解析状态和文档版本。

### 6.3 Event

从 DocumentVersion 中抽取可独立验证的现实动作或事实。一个 DocumentVersion 可以产生多个 Event，同一现实事项的不同阶段分别形成 Event，例如签约、开工和投产分别记录，不因属于同一项目而相互覆盖。Event 包括：

- 事件主体和对象；
- 时间、区域及产业概念；
- 措施或行动；
- 金额、数量、期限和阶段；
- 规划、申报、入选、签约、开工、投产、采购等事件类型；
- 证据、来源和独立事件组。

同一现实发生事项可能由多个文档重复报道，这些 Event 通过 IndependentEventGroup 合并为一个独立信号。

### 6.4 IndependentEventGroup

表示同一现实发生事项对应的独立信号，用于合并转载、重复报道和对同一事项的近似表述。变化统计中的独立事件数量以 IndependentEventGroup 为单位。

同一项目在签约、开工、投产等不同阶段形成不同的 IndependentEventGroup，并通过共同项目、主体或关联事件关系连接，既避免重复计数，也保留阶段推进信息。

### 6.5 Evidence

表示 Event 字段或分析结论与原始材料之间的证据关系。Evidence 引用明确的 DocumentVersion，并记录支持内容所在的正文片段、附件页码、表格行或其他可定位位置。一个 Event 可以有多条 Evidence，一条 Evidence 也可以支持多个相关字段。

### 6.6 Topic

表示从独立事件和文档特征中归纳的技术、产品、应用或产业主题，保存同义词、上下位关系、关联实体、时间序列指标和聚类版本。Topic 是用于持续监测、聚类和变化检测的观察对象，可以处于边界不完整或业务价值尚未验证的状态，不能直接作为正式赛道发布。

### 6.7 Track

表示通过业务验证的稳定对象。赛道是一组具有共同经营活动、可观察企业特征、相对稳定产业链角色，并可能产生相似、可复制 IT 需求的企业集合；同时有持续或多类型外部信号支持。Track 与 Topic 分开管理，只有通过赛道验证门槛的 Topic 或 Topic 组合才能形成 Track。

Track 至少包含：

- 稳定赛道 ID、名称和版本；
- 定义、纳入范围和排除边界；
- 上下位赛道及相邻主题；
- 产业链环节和企业参与角色；
- 相关技术、产品、应用、资质、园区和关键词；
- 支持事件及来源；
- 生命周期和置信度；
- SMB 适配评估；
- 未知项、争议项和复核状态。

### 6.8 TrackRegionSnapshot

表示赛道在特定区域和时间窗口内的影响情况，保存该区域的影响依据、支持信号、发展阶段、热度和 SMB 条件。区域记录只覆盖有证据支持的主要区域和热门区域，不将所有理论上可能受影响的地区全部列入。

区域是否纳入不以存在当地政策或新闻为唯一条件。即使缺少直接政策或新闻信号，只要企业集群、产业基础、项目分布或其他可靠材料能够证明赛道在当地具有显著影响，也可以列为主要区域；此时应明确记录直接信号缺失及实际使用的影响依据。

### 6.9 MetricSnapshot

保存指定主题、赛道或赛道区域在一个时间窗口内的指标，使本期与上一期、历史基线能够稳定比较。

核心对象关系为：`Source → Document / DocumentVersion → Event → IndependentEventGroup → Evidence → Topic → 候选赛道验证 → Track → TrackRegionSnapshot`。Evidence 同时保留从 Event 和分析结论回溯到 DocumentVersion 的引用关系。

## 七、采集与处理架构

### 7.1 采集方式

按来源能力选择适配器：

- 官方 API 或结构化接口；
- RSS、站点地图或栏目列表页；
- 静态 HTML 抓取；
- 搜索 API 发现 URL；
- PDF、Word、Excel、WPS 等附件下载；
- 必要时使用浏览器自动化处理少量动态页面。

采集任务只处理新增或发生变化的对象。使用 URL 规范化、发布时间、HTTP 缓存信息、文件哈希和正文哈希避免重复下载与重复分析。

### 7.2 文档解析

程序优先完成：

- 正文和元数据提取；
- 附件类型识别；
- 表格及名单解析；
- 日期、金额、地区和文号规则抽取；
- 精确去重和近似去重；
- 转载与原始来源关联；
- 解析质量评分。

扫描件 OCR 作为独立能力处理。低质量 OCR 不单独支持关键事实。

### 7.3 存储

POC 至少区分：

- 原始层：HTML、附件、抓取响应和原始元数据；
- 标准层：Document、Event 和实体对象；
- 分析层：Topic、Track、时间窗口指标和 SMB 评估；
- 发布层：赛道注册表、周期报告、Dashboard 数据和质量报告。

原始层不可由后续模型输出覆盖；派生对象记录输入版本、规则版本和模型版本。

## 八、事件抽取与主题识别

### 8.1 确定性抽取

使用规则、词典和传统 NLP 批量提取：

- 发布时间、生效时间和申报期限；
- 发布机构、地区、文号和政策层级；
- 金额、数量、企业名单和项目名单；
- 规划、补贴、申报、示范、采购、建设、投产等事件类型；
- 技术、产品、应用场景、园区和企业实体。

POC 首版 Event 分类包括：

- `policy_measure`：政策、规划和扶持措施；
- `application_program`：项目申报、征集和补贴申请；
- `recognition_result`：名单、试点、示范和资质认定；
- `project_progress`：项目签约、开工、建设、投产、扩建和停建；
- `procurement_activity`：采购意向、招标、中标和合同；
- `investment_financing`：产业基金、投资、融资和并购；
- `business_operation`：产品发布、产能建设、订单和商业部署；
- `standard_release`：标准和技术规范的立项、发布与实施；
- `statistical_observation`：带有时间、区域、指标、数值和单位的产业统计事实。

Document 类型描述材料形式，Event 类型描述材料中发生的现实动作或事实，两者分别管理。一份 Document 可以抽取多个 Event。Event 公共字段至少包括事件类型、阶段、主体、对象、动作、区域、文档发布时间、金额或数量、证据、独立事件组和置信度；不同事件类型按需增加专属字段。

同一主体、对象、动作阶段、区域和大致时间相同的重复报道合并为一个 IndependentEventGroup。同一项目的签约、开工和投产分别形成独立事件组并相互关联。一份名单的发布作为一个 Event，名单企业作为参与实体，不默认按企业拆成多个独立事件。

### 8.2 轻量分类与向量处理

使用可批量运行的分类模型和向量模型完成：

- 文档相关性和内容类型分类；
- 与已有主题的相似度匹配；
- 近似文档和同一事件识别；
- 主题聚类及异常主题发现；
- 高价值候选排序。

### 8.3 大模型任务

大模型仅用于：

- 复杂政策措施、适用对象和影响路径抽取；
- 模糊事件的语义核验；
- 相近主题的归并、拆分和命名；
- 赛道定义与边界草拟；
- 近期变化原因总结；
- SMB 影响和联想能力适配解释；
- 冲突证据和低置信候选复核。

模型调用按文档价值、规则置信度和候选新颖性触发，不对所有文档逐篇调用。相同输入及处理版本应缓存结果。

## 九、主题发现与赛道形成

### 9.1 双通道主题发现

主题发现采用两段式流程：新独立事件先执行已知主题匹配，能够稳定匹配的事件用于更新已有 Topic；无法稳定匹配的剩余事件再进入未知主题发现流程。

#### 已知主题匹配

维护可版本化的主题词典、同义词、上下位概念和向量表示，把新事件映射到已有 Topic，并更新相应时间窗口指标。

#### 未知主题发现

对无法稳定映射的剩余独立事件执行：

- 新词和突增词检测；
- 实体与关键词共现分析；
- 时间窗口聚类；
- 跨来源和跨区域聚类合并；
- 新颖性和持续性计算；
- 模型辅助命名及边界生成。

未知主题发现结果先形成新的 Topic 或更新已有 Topic，不直接形成 Track。系统随后根据相关 Topic、独立事件、企业经营活动和产业链角色形成候选赛道验证记录，通过四类硬门槛后再生成 Track。

系统必须同时具备两条通道，否则只能监测人工预先知道的方向，不能实现赛道挖掘。

新事件按照“词典和规则精确匹配、向量相似度匹配、企业经营活动及产业链角色校验”的顺序关联 Topic。高置信匹配更新已有 Topic；模糊事件可以关联多个 Topic 并分别保存分数；无法稳定匹配的事件进入剩余事件聚类。地域、发布机构或政策名称不同不单独触发新建 Topic。

无法匹配的聚类至少包含两个独立事件，并具有共同的技术、产品、应用或企业经营活动时，创建新的 Topic；单个独立事件只作为临时主题线索保留。

Topic 合并至少要求企业经营活动和主要产业链角色一致、事件或实体存在明显重合、无法形成稳定排除边界且 IT 需求没有实质差异。Topic 拆分至少要求内部形成持续稳定的事件子群，不同子群具有不同经营活动、产业链角色或 IT 需求，并且能够分别定义边界。地域差异和单次聚类结果变化不单独触发拆分。合并和拆分均保留原 ID、依据和映射关系。

候选赛道的 POC 初始进入条件为：至少三个独立事件、至少两个独立来源，并且涉及至少两种 Event 类型或信号出现在至少两个时间窗口；同时能够初步描述企业经营活动、产业链角色并生成第一版 SMB 经营价值映射。所有数量阈值均配置化，并根据人工审核结果调整。

### 9.2 候选赛道验证

候选 Topic 或 Topic 组合形成正式 Track 前，至少通过以下四类硬门槛：

- 信号成立：不是孤立事件，具备独立来源、持续性或多信号类型；
- 边界成立：能够明确纳入、排除以及相邻赛道；
- 企业集合成立：存在可描述、可识别的参与企业及产业链角色；
- 经营价值成立：能够说明可能产生的标准化 IT 需求及 SMB 覆盖路径。

未通过全部硬门槛的对象继续作为 Topic 或候选验证记录保留，不以 Track 名义正式发布，也不因需要达到预设赛道数量而降低门槛。

候选验证记录的状态包括：`candidate`、`watchlist`、`accepted` 和 `rejected`。程序根据结构化指标、规则、算法结果和有限模型判断自动执行四类门槛验证，状态为 `accepted` 的候选自动创建或更新 Track，不设置人工审批前置条件。正式 Track 的生命周期状态包括：`selected`、`cooling` 和 `archived`。候选判断和 Track 状态变化均保留历史，不覆盖旧版本。

## 十、近期变化检测

### 10.1 时间窗口

第一版至少维护：

- 最近 7 天；
- 最近 30 天；
- 最近 90 天；
- 上一对应周期；
- 过去 6 至 12 个月历史基线。

POC 首版暂不引入不同信号的衰减和有效期规则，统一在相同时间窗口内进行比较；不同信号的时效差异留待后续优化。

POC 阶段所有时间窗口和变化统计统一使用文档发布时间。首次发现时间和抓取时间继续保存，用于采集审计和问题定位，但不参与本阶段的趋势统计；历史回采材料按其原始发布时间进入对应历史窗口。无法可靠确定发布时间的材料可以保存和检索，但不进入时间变化指标。

### 10.2 变化指标

每个主题和赛道计算：

- 按来源总发布量归一化后的相关信号数量。相关信号以关联到该 Topic 或 Track 的不同 Document 为计数单位，同一 Document 对同一 Topic 或 Track 最多计一次；
- 独立事件数量；
- 独立来源数量及来源类型多样性；
- 涉及区域数量和新增区域；

上述指标分别与上一对应周期和历史基线比较。相关信号数量必须按来源总发布量进行归一化，避免把网站发布量上升误判为主题升温。POC 首版不根据政策层级、事件阶段、实体数量、新增关键词或信号衰减生成变化结论。

每个计划来源在每个统计周期内必须区分正常采集且无新增、采集失败、解析失败、历史材料延迟发现以及来源结构或发布机制变化等情况。来源缺失或处理失败不能按零信号计入趋势，也不能据此输出产业降温；受影响的主题、赛道和区域指标应标记数据不完整，并降低或暂停相应变化结论。

### 10.3 变化结论

变化结论拆分为活动状态和区域状态。活动状态输出：

- 新出现；
- 快速升温；
- 持续活跃；
- 热度回落；
- 信号不足。

区域状态输出：区域扩散、区域稳定或信号不足。区域状态与活动状态可以同时成立。

POC 使用以下可配置初始规则：

- 新出现：历史基线没有有效独立事件，当前窗口至少有两个独立事件和两个独立来源；
- 快速升温：归一化信号量达到上一周期与历史基线较高者的 1.5 倍以上，且独立事件至少增加两个；
- 持续活跃：当前至少有两个独立事件和两个独立来源，归一化信号量不低于历史基线的 80%，但未达到快速升温；
- 热度回落：数据完整时，归一化信号量低于历史基线的 50%，且独立事件至少减少两个；
- 信号不足：独立事件少于两个、独立来源少于两个，或者来源完整性不足以判断；
- 区域扩散：当前窗口至少新增一个有证据支持的区域，且涉及区域总数高于上一周期。

归一化信号量等于当前窗口相关 Document 数量除以同一可比来源集合的全部有效 Document 数量再乘以 1000。环比只使用两个周期均正常采集的共同来源。最近 30 天作为主要判断窗口，前 30 天作为上一周期，过去 6 至 12 个月的 30 天窗口中位数作为历史基线；最近 7 天用于短期提示，最近 90 天用于辅助观察持续性。

来源类型用于判断结论置信度：只有一种来源类型时为低置信，至少两种来源类型时可达到中等置信，来源类型多样且覆盖完整时可达到高置信。变化状态只表达外部信号活跃程度，不直接表示产业发展方向有利或实际采购需求增长。

变化结论保留指标、比较窗口和主要证据，不只输出模型生成的文字描述。

## 十一、面向联想 SMB 的评估

### 11.1 与大型政企洞察的区别

大型政企通常更关注国家战略、重大工程、财政规模、央国企参与和大型定制项目。联想 SMB 需要优先判断：

- 赛道是否存在数量充足的中小企业；
- 产业链和采购是否分散，而非被少数大型集团控制；
- 政策是否能实际触达中小企业；
- IT 需求是否标准化、可复制；
- 企业是否在近期进入投入和建设阶段；
- 客户是否能够通过区域、园区、行业和特征批量圈选；
- 联想 SMB 产品、渠道和服务体系是否能够覆盖。

### 11.2 SMB 适配维度

每个赛道分别输出以下判断，不在第一版压缩成不可解释的单一分数：

| 维度 | 核心问题 |
|---|---|
| 中小企业基础 | 是否存在数量和密度足够的中小企业及供应商 |
| 政策可达性 | 补贴、申报、试点和扶持条件是否面向中小企业 |
| IT 需求相关性 | 企业活动是否可能产生设备、算力、存储、网络、安全、研发设计或数字化需求 |
| 需求可复制性 | 需求是否适合标准化产品和规模化销售，而非大型定制集成 |
| 区域可经营性 | 是否形成园区、集群或可批量覆盖的地域分布 |
| 联想适配度 | 是否位于联想 SMB 已确认的产品和服务能力范围内 |

每个维度使用“强、中、弱、信息不足”，并保存依据和不确定性。外部热度高但 SMB 适配弱的方向进入观察或排除，不因宏观重要性自动成为重点赛道。

### 11.3 SMB 经营价值映射

SMB 经营价值采用“通用 IT 需求分类 + 可编辑映射表 + 模型初步生成 + 人工修订”的方式形成。该映射不是企业赛道标签，而是连接赛道经营活动、可能产生的 IT 需求和联想 SMB 能力的业务参考。

POC 先维护通用 IT 需求分类，包括办公与协同终端、研发设计与专业工作站、计算与 AI、存储与备份、网络连接、信息安全、现场与边缘计算以及运维服务。分类可以随实际赛道材料修订和扩展。

模型根据 Track 的定义、企业参与角色、经营活动、技术、产品和应用场景，初步生成映射表。每条映射至少记录：

- 企业角色和经营活动；
- 可能触发的 IT 需求类别及触发原因；
- 需求标准化和可复制程度；
- 可对应的联想 SMB 能力类别；
- 使用的赛道证据和推断说明；
- 置信度、生成方式和版本。

映射表支持人工编辑和修订。没有明确联想能力资料或证据不足时，对应字段保留“信息不足”或“待确认”，不由模型自行补全为确定结论。Track 的 SMB 评估和区域 SMB 条件引用指定版本的映射表生成。

## 十二、赛道注册表及下游契约

本项目向客户标签项目发布版本化赛道注册表。每条正式赛道至少提供：

```json
{
  "track_id": "track_example",
  "version": "2026-W37",
  "name": "示例赛道",
  "status": "selected",
  "definition": "赛道定义",
  "inclusion": [],
  "exclusion": [],
  "roles": [],
  "keywords": [],
  "entities": [],
  "technologies": [],
  "products": [],
  "applications": [],
  "qualifications": [],
  "region_snapshots": [
    {
      "region_code": "example_region",
      "region_name": "示例区域",
      "region_roles": ["major", "hot"],
      "impact_evidence_ids": [],
      "supporting_signal_ids": [],
      "stage": "implementation",
      "heat": "rising",

  "smb_assessment": {},
```

`region_snapshots` 只发布有证据支持的主要区域和热门区域，不表示赛道影响范围的穷举。区域可以没有直接政策或新闻信号，但必须有其他可追溯依据支持其作为主要区域；直接信号为空时不得自动解释为该区域不受影响。

Track 由程序自动分析和生成，不设置人工审批前置条件。人类可以编辑和修订自动生成的最终结果；人工修订形成新的结果版本，保留被修订版本、修改内容和修改依据，不静默覆盖自动生成结果。

最终看板应支持用户通过可视化界面编辑和修订结果。POC 当前只要求数据结构和版本机制能够支持后续编辑，不在本阶段展开具体页面、交互和权限设计。

下游只消费已发布版本，不直接读取模型中间结果。赛道名称调整、拆分、合并和状态变化必须保留映射关系，避免客户标签随周报无解释漂移。

## 十三、运行与可扩展性设计

### 13.1 调度单元

任务拆分为：

- 来源发现；
- 页面和附件采集；
- 文档解析；
- 去重与版本识别；
- 实体和事件抽取；
- 向量化和主题匹配；
- 变化指标计算；
- 候选赛道验证；
- SMB 评估；
- 发布与质量审计。

只有可以独立缓存、重试或复用的步骤才拆成任务，避免为了形式完整产生大量重复模型调用。

### 13.2 运行要求

- 任务幂等；
- 支持有限并发、限流、重试和断点恢复；
- 输入、规则、模型和输出均有版本；
- 单对象失败隔离；
- 所有降级和人工覆盖可见；
- 配置或模型变化只使受影响的派生结果失效；
- Dashboard 和报告从已校验结构化结果确定性生成。

### 13.3 技术形态

POC 采用单机部署的模块化单体和持久化批处理管道，数据模型和任务接口不绑定本地目录。使用：

- 关系数据库作为元数据、任务状态、业务对象和引用关系的事实来源；
- 对象存储保存网页快照及附件；
- 全文检索与向量索引支持检索、去重和主题匹配；
- 持久化任务表或轻量工作流引擎调度增量处理，记录输入版本、执行状态、重试和失败原因；
- 配置化来源适配器和处理器注册机制。

第一版不要求分布式部署，但不得把全量状态只保存在一次进程或 Agent 上下文中。

## 十四、质量与验收指标

现阶段不存在权威赛道分类标准，也没有库内企业的正确赛道标签。POC 不以监督学习准确率或与既有标签的一致率作为验收依据。文档、事件、Topic、Track、变化结论和 SMB 评估均通过人工抽样或逐项审核判断；人工建议用于修订结果和调整规则，不被追溯性地视为预先存在的标准答案。

### 14.1 数据管道

- 计划来源采集成功率；
- 新增页面发现延迟；
- 正文及附件解析成功率；
- 精确和近似去重效果；
- 元数据完整率；
- 单文档平均处理成本；
- 局部失败恢复成功率。

### 14.2 事件与主题

- 人工抽样审核文档相关性判断；
- 人工抽样审核关键事件字段及证据；
- 人工抽样审核同一事件合并和独立事件计数；
- 人工抽样审核已知主题匹配；
- 人工审核新主题候选的有效性；
- 人工复核工作量。

### 14.3 赛道结果

- 正式赛道证据覆盖率；
- 多来源和多信号支持比例；
- 赛道定义及边界可判定性；
- 周期间状态稳定性；
- 新增、升温和降温结论的解释性；
- 人工审核赛道定义、证据、区域和 SMB 判断的合理性；
- 下游能否依据赛道定义执行企业筛选和标签化。

业务提供的库内企业基本信息和工商信息不包含赛道标签，不能作为 Track 发现或企业赛道分类准确率的标准答案。该数据后续只用于验证赛道定义、纳入排除特征及数据契约是否具备可执行性。

### 14.4 成本与规模

- 每周新增文档量和实际处理吞吐；
- 每千篇文档模型调用次数；
- 每个正式赛道的模型及计算成本；
- 缓存命中率；
- 从采集到发布的总耗时。

POC 的规模化成立条件不是能够并发调用更多 Agent，而是原始数据量增长时，模型调用量只随高价值候选增长，不与全部文档近似线性增长。

## 十五、POC 实施范围

### 阶段一：数据底座与历史回采

- 建立来源注册表；
- 接入中央核心来源和一个目标区域；
- 实现 HTML 与常见附件采集、标准化、去重和持久化；
- 回采至少十二个月材料；
- 建立采集和解析质量报告。

完成标准：能够连续增量运行，原始材料和标准化文档可追溯、可复跑。

### 阶段二：事件与变化检测

- 建立政策及产业事件分类；
- 实现确定性字段抽取和有限模型抽取；
- 建立主题词典、向量匹配和时间窗口指标；
- 输出主题近期变化及证据。

完成标准：能够用历史基线解释主题变化，不依赖一次性搜索结论。

### 阶段三：赛道形成与 SMB 评估

- 建立已知与未知主题双通道；
- 形成完整候选池；
- 实现赛道归并、边界、生命周期和证据校验；
- 增加 SMB 适配评估；
- 发布版本化赛道注册表和周期洞察。

完成标准：重点赛道不是预设的少量示例，候选、观察、排除和状态变化均有记录。

### 阶段四：覆盖扩展与成本验证

- 扩展到三个代表性区域；
- 接入采购、统计、项目和有限行业资讯；
- 验证批量处理、失败恢复和成本曲线；
- 完成人工结果审核及下游标签项目数据契约可执行性验证。

完成标准：新增来源和区域不要求重写核心流程，运行成本和模型使用量处于可接受范围。

## 十六、不在当前范围内

- 全国所有政府及行业网站的完整覆盖承诺；
- 精确市场规模、增长率和利润池测算；
- 复杂产业知识图谱；
- 对全部原始文档逐篇使用大模型；
- 企业联系人和联系方式挖掘；
- 库外新客户发现；
- 库内客户标签批量生产；
- CRM 商机认定、线索分配和自动触达；
- 销售话术生成；
- 无证据支持的采购需求和收入预测。

## 十七、主要风险与控制

| 风险 | 控制方式 |
|---|---|
| 地方网站结构差异和改版 | 来源适配器隔离、健康监测、通用解析器与站点特例分离 |
| 免费来源覆盖不足 | 明确覆盖清单，使用搜索补漏，预留商业数据适配器 |
| 历史数据不足 | POC 首期执行十二至二十四个月回采，不用单期材料宣称趋势 |
| 转载造成虚假热度 | 原始来源追溯、近似去重和独立事件组 |
| 文章发布量变化造成偏差 | 使用主题占比、来源多样性及历史归一化指标 |
| 预设词典漏掉新赛道 | 已知主题匹配与未知主题聚类并行 |
| 聚类结果噪声过大 | 最小来源、持续性、事件类型和边界门槛，模型只辅助命名和复核 |
| 模型成本失控 | 前置规则和轻量模型、候选触发、批处理、缓存和调用预算 |
| 模型结论漂移 | 固定输入、提示词、模型和规则版本，正式结果经过确定性校验 |
| 宏观热点不适合 SMB | 独立 SMB 适配评估，不以外部热度自动入选 |

## 十八、最终交付物

第一阶段项目最终交付：

1. 来源注册表及覆盖说明；
2. 原始文档、附件和标准化文档库；
3. 结构化事件及证据关系；
4. 主题库、时间序列指标和变化记录；
5. 全部赛道候选及其状态；
6. 版本化正式赛道注册表；
7. 面向联想 SMB 的周期赛道洞察；
8. 数据管道、覆盖、模型使用和业务质量报告；
9. 可直接供客户标签项目消费的数据契约。

系统是否成功以可持续采集、历史变化检测、赛道发现质量、SMB 适配性、证据可追溯性和单位处理成本共同判断，不以单次报告展示效果或少数代表性赛道作为验收标准。
