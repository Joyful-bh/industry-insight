# 赛道洞察 POC 实现方案

## 一、POC 目标

本阶段建设一条可重复运行的北京地区赛道洞察链路，将指定网站中的政策与行业材料转化为结构化事件、产业 Topic 和候选 Track，并通过人工审核评价结果质量。

POC 验证以下能力：

1. 指定来源中的政策与行业材料能够稳定采集、解析和筛选。
2. 相关材料能够转化为带有原文证据的结构化产业事件。
3. 多条事件能够聚合为含义清晰的产业 Topic。
4. Topic 能够形成满足信号、边界、企业集合和经营价值门槛的候选 Track。
5. Track 能够形成面向联想 SMB 业务的 IT 需求和覆盖路径判断。

## 二、对象定义

### 2.1 Event

Event 表示材料中一项可以独立描述的政策或产业事实。一篇材料可以产生零到三条 Event。

首版事件类型包括：

- `policy_support`：政策、规划、申报、资金、试点和认定；
- `project_delivery`：签约、开工、投产、扩建、园区和集群建设；
- `investment_financing`：融资、投资和并购；
- `business_operation`：产品、业务、订单、合作和市场扩张；
- `technology_industrialization`：技术突破、成果转化、标准和产业协作；
- `market_change`：需求、供给、价格、产能和景气变化。

### 2.2 Topic

Topic 是从一组相关 Event 中形成的产业观察对象，描述反复出现的技术、产品、应用场景、企业经营活动或产业方向。

### 2.3 Track

Track 是通过业务验证的稳定对象，定义为：

> 一组具有共同经营活动、可观察企业特征、相对稳定产业链角色，并可能产生相似、可复制 IT 需求的企业集合；同时有持续或多类型外部信号支持。

候选 Track 按以下四类门槛审核：

- 信号成立：具备独立来源、持续性或多种信号类型；
- 边界成立：具备明确的纳入范围、排除范围和相邻方向；
- 企业集合成立：具备可描述的参与企业、经营活动和产业链角色；
- 经营价值成立：具备可标准化的 IT 需求和 SMB 覆盖路径。

## 三、实现范围

### 3.1 数据范围

- 目标区域：北京市；
- 时间范围：最近 24 个月；
- 来源范围：来源配置中启用的政府、园区、产业组织、企业及市场媒体网站；
- 文档格式：HTML 和 PDF；
- 时间统计口径：文档发布时间；
- 运行方式：单机、PostgreSQL、本地 BlobStore 和命令行批处理。

### 3.2 输出范围

POC 输出以下结果：

- 来源采集与解析状态；
- 文档相关性分类结果；
- Event 结构化数据及证据；
- Topic 聚类结果及定义；
- 候选 Track 及四类门槛判断；
- Track 的北京主要影响区域；
- Track 的 SMB IT 需求映射；
- JSON 结果和 Markdown 审核报告。

## 四、处理流程

```text
来源配置
  → HTML/PDF 采集
  → 正文解析与标准化
  → 文档相关性筛选
  → LLM 事件抽取
  → 事件基础去重
  → Event 向量化与聚类
  → LLM 生成 Topic
  → LLM 生成候选 Track
  → 四类门槛审核
  → SMB IT 需求映射
  → JSON 与 Markdown 报告
```

各步骤通过数据库中的稳定标识衔接，可以独立运行和重复执行。

## 五、已有数据底座

### 5.1 来源与采集

来源通过 YAML 配置管理，记录来源代码、入口、地区、内容类型、适配器、限速、筛选条件和启用状态。

采集模块提供：

- 通用列表页采集；
- 站点薄适配器；
- HTML 与 PDF 下载；
- 翻页和 24 个月截止控制；
- 请求限速、失败记录和有限重试；
- 页级即时检查点；
- 全来源批次恢复；
- URL 与内容哈希幂等；
- 原始内容寻址存储。

### 5.2 文档解析

文档解析模块提供：

- HTML 正文提取；
- PDF 文本提取；
- 标题和发布时间整理；
- 模板噪声清理；
- 附件关联；
- 正文哈希和解析版本记录。

### 5.3 相关性筛选

相关性筛选采用两级流程：

1. 程序规则完成高置信相关、可能相关和低相关分类。
2. LLM 对 `possibly_relevant` 文档进行结构化复判。

每次分类保存分类结果、理由、规则版本、模型版本和输入文档版本。

## 六、Event 抽取实现

### 6.1 输入

事件抽取处理状态为 `relevant` 的标准化文档版本。模型输入包括：

- 文档标题；
- 发布时间；
- 发布机构和来源；
- 正文；
- 附件正文；
- 已识别地区信息。

### 6.2 LLM 输出

模型每次返回零到三条事件，每条事件包含：

| 字段 | 内容 |
|---|---|
| `event_type` | 六类事件之一 |
| `summary` | 一句话事件描述 |
| `subjects` | 政府、企业、园区、机构等主体 |
| `action` | 事件中的主要动作 |
| `objects` | 政策对象、项目、产品或产业对象 |
| `industries` | 产业、技术、产品和应用场景 |
| `companies` | 涉及企业 |
| `regions` | 涉及区域 |
| `industry_roles` | 产业链角色 |
| `event_time` | 材料中明确出现的事件时间 |
| `evidence_quote` | 支持事件的原文片段 |
| `confidence` | 模型置信度 |

### 6.3 校验与入库

程序完成以下处理：

- JSON Schema 校验；
- 事件类型枚举校验；
- 证据片段在正文中的存在性校验；
- 字段长度和数量限制；
- 文档版本、抽取器版本和事件序号幂等；
- 失败任务记录和重试；
- 模型、提示词和运行批次记录。

Event 使用一张主表保存结构化字段、证据、来源文档版本和处理版本。

### 6.4 基础去重

事件使用以下特征生成重复候选：

- 主要主体；
- 事件类型；
- 核心动作；
- 项目或对象名称；
- 地区；
- 发布时间邻近程度；
- 事件摘要文本相似度。

高相似事件共享一个 `duplicate_group_key`。每个分组保留全部来源记录，并选择一条代表事件用于 Topic 聚类。

## 七、Topic 生成实现

### 7.1 聚类输入

每条代表 Event 生成一段聚类文本，内容包括：

- 事件摘要；
- 产业、技术和产品；
- 企业经营活动；
- 产业链角色；
- 应用场景；
- 事件类型。

### 7.2 聚类方法

1. 使用中文文本向量模型生成 Event 向量。
2. 使用余弦距离进行层次聚类。
3. 按距离阈值产生初步事件簇。
4. 为每个事件簇选择距离中心较近的代表事件。
5. 将代表事件、关键词、企业和地区分布提交给 LLM。
6. LLM 生成 Topic 名称、定义、关键词、范围和支持事件摘要。

聚类阈值、最小事件数和向量模型通过配置管理。

### 7.3 Topic 数据

每个 Topic 保存：

- Topic ID；
- 名称和定义；
- 关键词与同义表达；
- 产业、技术、产品和应用场景；
- 企业经营活动和产业链角色；
- 支持 Event；
- 涉及来源和区域；
- 聚类参数、模型版本和分析批次。

## 八、候选 Track 生成

### 8.1 生成输入

候选 Track 生成使用：

- Topic 定义与关键词；
- 支持 Event 及证据；
- 独立来源数量；
- 事件类型分布；
- 时间分布；
- 企业、项目和地区分布；
- 企业经营活动和产业链角色。

### 8.2 Track 输出

LLM 为每个候选生成：

- Track 名称；
- Track 定义；
- 纳入范围；
- 排除范围；
- 相邻 Topic；
- 企业经营活动；
- 产业链角色；
- 可观察企业特征；
- 主要影响区域；
- 支持 Event 和证据；
- 四类门槛判断及说明；
- 待人工确认项。

程序计算信号门槛中的事件数量、来源数量、事件类型数量和时间分布。人工审核完整 Track 结果并记录修订后的有效值。

## 九、变化判断

每个 Topic 和候选 Track 使用两个时间窗口：

- 近期窗口：最近 90 天；
- 历史窗口：近期窗口之前的回采数据。

统计指标包括：

- 归一化相关信号数量；
- 独立事件数量；
- 独立来源数量；
- 来源类型数量；
- 涉及区域数量；
- 新增区域数量。

首版变化状态包括：

- `recently_emerged`：近期形成新的持续信号；
- `heating_up`：近期指标相对历史窗口明显增加；
- `stable`：近期指标处于历史常见范围。

每个状态保存指标值、比较窗口和判定依据。

## 十、SMB 经营价值生成

SMB 经营价值采用“通用 IT 需求分类、可编辑映射表、模型生成和人工修订”的处理方式。

通用 IT 需求分类包括：

- 终端与移动办公；
- 算力与工作站；
- 服务器、存储和备份；
- 网络与连接；
- 云与混合基础设施；
- 数据管理与分析；
- 人工智能应用；
- 信息安全；
- 生产数字化与边缘计算；
- 协同办公与业务软件；
- 运维与设备生命周期服务。

模型根据 Track 的企业经营活动、产业链角色、应用场景和可观察特征生成：

- 可能的 IT 需求；
- 需求触发原因；
- 适用企业角色；
- 标准化和复制程度；
- SMB 客户识别条件；
- 销售或渠道覆盖路径；
- 结论置信度和证据。

## 十一、数据结构

POC 使用以下核心对象：

```text
Source
  → Document
  → DocumentVersion
  → RelevanceResult
  → Event
  → Topic
  → Track
  → AnalysisRun
```

`AnalysisRun` 记录数据截止时间、来源配置版本、规则版本、模型版本、提示词版本和生成结果，用于复现一次完整分析。

## 十二、命令行任务

处理链路提供以下命令：

```text
source-sync           同步来源配置
collect-source all    执行全来源采集
parse-enqueue         创建文档解析任务
parse-work            执行文档解析
relevance-enqueue     创建相关性分类任务
relevance-work        执行相关性分类
event-enqueue         创建事件抽取任务
event-work            执行事件抽取
event-status          查看事件抽取进度
topic-build           生成一次 Topic 聚类结果
track-build           生成候选 Track
report-build          生成 JSON 与 Markdown 报告
```

所有命令支持按批次重复运行，并输出处理数量、成功数量、失败数量和待处理数量。

## 十三、实施阶段

### 阶段一：Event 抽取闭环

交付内容：

- Event 数据表和数据库迁移；
- LLM 事件抽取提示词；
- 结构化输出模型与校验；
- 事件任务入队、执行和状态命令；
- 幂等、失败记录和重试；
- 真实文档抽样审核结果。

### 阶段二：Topic 聚类

交付内容：

- Event 聚类文本；
- 文本向量生成；
- 层次聚类；
- LLM Topic 命名与定义；
- Topic、Event 关联数据；
- Topic 审核报告。

### 阶段三：候选 Track 与变化判断

交付内容：

- 候选 Track 生成；
- 四类门槛指标和语义判断；
- 近期窗口与历史窗口统计；
- 变化状态；
- 北京主要影响区域汇总。

### 阶段四：SMB 价值与结果报告

交付内容：

- 通用 IT 需求映射表；
- Track SMB 价值生成；
- 人工修订值保存；
- 机器可读 JSON；
- 人工审核 Markdown 报告。

## 十四、人工审核与验收

### 14.1 Event 抽样

从政策、园区、产业组织、企业动态和市场媒体中选择 30～50 篇真实相关文档，审核：

- 事件拆分是否合理；
- 事件类型是否正确；
- 主体、动作、对象、产业和地区是否准确；
- 证据片段是否直接支持事件；
- 关键信息遗漏比例；
- 重复事件分组质量。

### 14.2 Topic 审核

审核每个 Topic 的：

- 簇内事件一致性；
- Topic 名称和定义；
- 产业粒度；
- 企业经营活动和产业链角色；
- 支持来源和事件数量。

### 14.3 Track 审核

审核每个候选 Track 的：

- 信号成立情况；
- 纳入、排除和相邻边界；
- 企业集合与产业链角色；
- IT 需求的标准化和复制程度；
- SMB 客户识别和覆盖路径；
- 引用证据与结论的一致性。

### 14.4 运行验收

完整链路验收记录：

- 各阶段输入和输出数量；
- 成功、失败和重试数量；
- 数据截止时间和配置版本；
- LLM 调用数量和 Token 消耗；
- 单批次运行时间；
- 人工审核结论及修订内容。

## 十五、POC 完成标准

POC 形成以下可交付成果：

1. 一批经过人工审核的结构化 Event。
2. 一组由真实事件支持的产业 Topic。
3. 一组完成四类门槛审核的候选 Track。
4. 每个 Track 的北京区域信号、近期变化和 SMB IT 需求判断。
5. 可复现的分析批次、JSON 数据和 Markdown 报告。
