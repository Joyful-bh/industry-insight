# 依据赛道挖掘客户名单项目交接说明

## 1. 文档目的

本文供后续“依据赛道挖掘相应客户名单”项目立项、设计和实施时使用，记录前序赛道洞察项目的业务背景、已有成果、可复用的数据边界，以及开发过程中已经验证过的问题处理方法和经验教训。

后续项目的目标不是重新发明赛道，也不是看到企业名称或行业关键词就直接贴标签，而是以指定版本的赛道定义为输入，从公开、合规的信息源中发现可能属于该赛道的企业，核验企业身份与经营活动，形成带来源、证据、置信度和处理版本的候选客户名单。

## 2. 整体项目背景

面向联想 SMB 业务的完整能力分为三个相互衔接、但运行边界独立的项目：

1. **赛道洞察**：持续采集政策、产业、项目、企业和市场信号，形成有证据支持的赛道定义与近期变化判断。
2. **库内客户标签**：接收已有企业库，依据指定版本的赛道定义判断企业是否属于相应赛道。
3. **库外客户名单挖掘**：从指定赛道出发，主动发现库外企业，核验其与赛道的关系，形成可复核的候选客户名单。本文件服务于这一新项目。

三个项目通过版本化赛道注册表传递信息，不共享运行状态，也不应互相读取对方的临时目录、数据库或内部缓存。前序项目负责回答“赛道是什么、边界在哪里、为什么值得关注”；新项目负责回答“哪些企业有公开证据表明属于这个赛道、它们扮演什么角色、为什么被纳入”。

联系人挖掘、个人信息收集、CRM 商机认定、销售话术、自动触达和未经核验的销售线索扩散，不属于客户名单挖掘的首期核心范围。

## 3. 前序赛道洞察项目做了什么

前序项目已建立以下完整链路：

```text
研究范围
→ 研究计划
→ 联网搜索与候选来源筛选
→ 页面抓取、正文解析和去重
→ 带原文证据的产业事件
→ 产业 Topic
→ 候选赛道生成与归并
→ 赛道边界、企业特征和 SMB 价值分析
→ 结构化数据与业务看板
```

程序负责来源管理、任务调度、状态保存、幂等、失败重试、断点恢复、结构校验和看板渲染；阿里云百炼模型负责研究规划、联网搜索、复杂语义抽取、主题归并、边界判断和解释生成。正式结论可以沿“赛道—Topic—事件—网页—原文证据”反向追溯。

赛道不是一个热词，而是一组具有共同经营活动、可观察企业特征、相对稳定产业链角色，并可能产生相似、可复制 IT 需求的企业集合。政策工具、技术概念、应用行业、采购方和供应方不能仅因语义相关就混成同一赛道。

## 4. 前序项目的实际成果

### 4.1 北京市制造业完整闭环验证

前序项目曾以北京市制造业、2024 年 9 月至 2026 年 9 月为范围跑通完整流程：

| 产物 | 数量 |
| --- | ---: |
| 产业事件 | 400 |
| 产业主题 Topic | 259 |
| 候选赛道 | 53 |
| 观察中赛道 | 40 |
| 赛道总数 | 93 |
| 已完成分析的赛道 | 93 |

这次运行证明了从研究范围到证据、赛道分析和看板的完整链路能够工作，也验证了任务持久化与中断恢复。它是流程闭环验证，不代表已经获得长期可比的升温或降温趋势；趋势判断仍需要多期、同口径的历史数据。

### 4.2 全国范围最新看板

当前正式看板生成于 2026 年 10 月 12 日，面向全国制造业范围，内含：

| 产物 | 数量 |
| --- | ---: |
| 赛道总数 | 704 |
| 候选赛道 | 565 |
| 观察中赛道 | 139 |
| 具有省级支撑信号的赛道 | 661 |
| 看板内可追溯 Topic | 5,816 |
| 看板内可追溯事件 | 9,168 |
| 已生成 SMB 产品关联分析的赛道 | 704 |

看板中的赛道涉及装备制造、新能源汽车、电池与储能、机器人、航空航天、半导体、工业软件、生物医药、新材料、食品加工等多个方向。完整成果位于 `reports/track_dashboard_latest.html`。

上述数量必须结合以下限制理解：

- 事件和 Topic 可以支撑多个赛道，不能把赛道引用数相加后当成独立事件总量。
- `candidate` 表示已具备当前规则要求的身份依据，`watchlist` 表示仍需补充证据；二者都不等于已经完成商业优先级确认。
- 当前全国目录仍存在宽泛父赛道与具体子赛道并存、相近名称重复、产业链角色边界不完全一致、单一事件形成长尾赛道等现象。
- 全国看板是赛道发现和审查成果，不应原样作为客户挖掘程序的无条件全量输入。正式运行前应先选定赛道版本，并完成人工抽查或目录治理。

### 4.3 新项目应接收的赛道数据

新项目不应解析看板 HTML，也不应只接收赛道名称。正式输入应是版本化、机器可读的赛道注册表，至少包含：

- `track_id`、注册表版本、状态和生效时间；
- 名称、别名、定义及目标企业原型；
- 核心产品与服务、经营活动和产业链角色；
- 纳入条件、排除条件和相邻赛道边界；
- 可公开观察的企业特征、关键词及关键实体；
- 适用地区和必要的时间边界；
- 支撑事件与来源引用；
- 当前不确定性、已知重叠和人工审核状态。

`track_id + registry_version` 应成为客户名单运行的固定输入。赛道定义变化后必须产生新版本，不能静默覆盖后继续复用旧名单。

从当前工作区可见交付物看，全国结果主要保存在运行数据库和人类可读看板中，尚不能把看板文件本身视为已冻结的下游数据接口。因此，新项目正式开工前还需要完成一次明确的交接动作：从结构化结果中筛选拟使用的赛道，处理明显重复和边界冲突，补齐稳定 `track_id`，通过人工抽查后导出带版本号的 JSON 或表格快照。该快照才是新项目的基线输入；看板只用于审阅和追溯。

## 5. 客户名单挖掘项目的基本原则

### 5.1 发现与核验分开

发现阶段追求召回率，可以使用搜索、公开目录、园区名录、行业协会、展会名录、企业官网和商业数据源发现候选企业；核验阶段必须逐企确认企业主体、经营活动、产业链角色及赛道边界。被搜索到不等于属于赛道，标题或摘要中出现关键词也不等于有充分证据。

### 5.2 企业主体与网页提及对象分开

网页可能同时出现政策发布方、园区、投资方、采购方、使用方、供应商和项目承建方。程序必须识别真正被判断的企业主体，并区分：

- 生产或提供赛道核心产品与服务的企业；
- 提供上游材料、零部件或配套服务的企业；
- 采购、使用或应用相关产品的企业；
- 仅被新闻顺带提及、没有可核验经营活动的主体。

不能因为一家制造企业使用机器人、人工智能或储能系统，就把它归为机器人、AI 或储能供应商。

### 5.3 事实、推断和业务判断分层

- **事实**：企业官网、工商信息、政府公示、招投标、产品资料等来源直接说明的内容。
- **推断**：由多项事实推导出的产业链角色或赛道归属，必须说明推断路径和不确定性。
- **业务判断**：客户价值、优先级、潜在 IT 需求等后续判断，不能反向冒充企业归属证据。

正式名单中的每个纳入结论都必须绑定来源 URL、来源类型、发布时间或访问时间、证据摘录、赛道版本、处理版本和置信度。证据不足时输出“待核验”或“不纳入”，不能用常识补齐事实。

### 5.4 候选名单不是最终销售名单

系统输出的是在指定来源覆盖和时间窗口内发现、并经过证据核验的候选企业。没有被发现不代表企业不属于赛道；发现数量少也可能是来源覆盖、网站访问或企业公开披露不足。后续仍需进行主体去重、存续状态检查、规模筛选、合规审查及业务审核。

## 6. 出现问题时的分析和处理方法

### 6.1 先记录现象，不先写原因

问题描述必须先包含：

- 预期结果；
- 实际结果；
- 可复现的输入、命令和运行版本；
- 出错阶段与最小失败对象；
- 日志、状态、原始响应或产物差异；
- 是否稳定复现。

“模型变笨了”“网络不好”“数据不行”“缓存乱了”都只是未经验证的假设，不能作为问题结论。

### 6.2 沿处理链路定位故障层

按以下顺序检查，不跨层猜测：

| 层级 | 需要核对的证据 |
| --- | --- |
| 输入 | 赛道版本、字段完整性、企业主体、地区、时间窗和编码是否正确 |
| 来源 | 搜索是否实际返回、来源是否可访问、页面是否为正文、发布时间是否可靠 |
| 网络与权限 | DNS、代理、沙箱网络、证书、API 权限、额度、限流和区域端点 |
| API | 请求参数、模型名称、工具能力、请求 ID、状态码及原始响应 |
| 解析与结构化 | 正文是否完整、字段映射、Schema、枚举、引用和证据逐字匹配 |
| 业务判断 | 企业角色、纳入排除条件、父子赛道、相邻赛道及置信度依据 |
| 状态与缓存 | 输入指纹、处理版本、任务状态、缓存命中和恢复边界 |
| 汇总与展示 | 数据查询、去重、统计口径、导出字段和模板版本 |

例如“企业没有被找到”至少可能源于查询覆盖不足、搜索权限失败、网站不可访问、企业别名未识别、候选被预筛误删、主体去重错误或核验规则过严。没有逐层证据时，不能直接断言市场上没有这类企业。

### 6.3 建立可证伪的假设

每个原因假设都要同时写出支持证据和反证方法。例如：

| 假设 | 支持证据 | 验证或证伪方法 |
| --- | --- | --- |
| 沙箱没有外网权限 | 域名解析或连接测试失败，API 未收到请求 | 在获准网络环境运行同一最小请求 |
| 模型输出漏项 | 原始输入存在对象，原始响应未返回，Schema 又允许省略 | 用要求逐项归属的契约重放同一批输入 |
| 赛道定义过宽 | 多个不同供应角色均满足同一纳入规则 | 用代表企业集检查角色和排除条件，拆分边界后回归 |
| 看板结果不一致 | 中间结构化数据一致，但 HTML 结构或样式不同 | 比较渲染器、模板、静态资源和数据适配层版本 |

一次只改变一个关键变量，并保留前后输入与结果。不能同时换模型、改提示词、调阈值和换数据，然后凭结果改善猜测真正原因。

### 6.4 在真正出错的层修复

- 网络权限问题通过运行权限、代理或网络前置检查解决，不能记成“来源无内容”。
- Schema 允许漏项时修契约和完整性校验，不能只在提示词里要求“务必完整”。
- 赛道边界错误时修定义、角色和纳入排除条件，不能靠增加关键词掩盖。
- 模板或数据适配错误时修渲染链路，不能用“配置不同”解释实际流程差异。
- 缓存键缺少版本时修输入指纹，不能默认删除全部数据库。

修复后必须回放原失败样本，并增加能阻止同类问题再次出现的回归检查。

### 6.5 验证完整效果，而不只验证“命令成功”

至少检查：

1. 输入文件和正式源码未被意外修改；
2. 阶段数量、顺序和业务参数符合设计；
3. 每条正式结论可以追溯到证据；
4. 中断后只重跑未完成或输入已变化的任务；
5. 同配置、同输入和固定外部响应下，结构化结果一致；
6. 导出字段、统计口径、样式模板和交付路径正确；
7. 独立环境运行不依赖开发者机器的绝对路径、全局依赖或历史缓存。

## 7. 必须避开的坑

### 7.1 不认真分析原因，直接主观臆断

这是最需要禁止的做法。典型表现包括：

- 看到零结果就说“市场上没有企业”；
- 看到网页抓取失败就说“来源没有信息”；
- 看到运行结果不同就说“配置不同很正常”；
- 看到模型输出少就说“模型能力不够”；
- 看到历史错误字段就说“流程仍未完成”；
- 看到关键词相似就认定两条赛道可以合并；
- 看到企业使用某项技术就认定它是该技术的供应商。

正确要求是：任何原因判断必须能指出直接证据、替代解释和验证方法。证据不足时只能写“尚未定位”，不能把推测包装成事实。宁可暂缓修复，也不要依据未经验证的判断改动正式规则和数据。

### 7.2 把研究范围标签当成事实发生地

搜索任务中的地区表示调查目标，不证明网页中的事件实际发生在该地区。企业注册地、总部所在地、项目所在地、工厂所在地和服务覆盖地必须分别提取。未知地区不能根据查询词自动补全。

### 7.3 把未知日期当成满足时间范围

搜索命中时间、页面更新时间、抓取时间和事件发生时间不是同一概念。发布日期或事件时间无法可靠确定时，可以保留材料，但不能把它当成指定窗口内的有效信号。

### 7.4 把采集失败当成零信号

网站受限、链接失效、解析失败、API 失败和预算停止都表示数据不完整，不表示没有企业或产业活动。失败对象要单独计数并保留原因，不能参与“无结果”“降温”或低覆盖结论。

### 7.5 只按名称或关键词判断企业归属

赛道名可能过宽、过窄或存在父子重叠；企业名称通常更不能说明经营活动。必须以赛道定义、产品服务、企业角色、纳入排除条件和直接证据共同判断。关键词只能用于召回，不能单独作为正式结论。

### 7.6 混淆供应方、使用方和关联方

政策支持对象、投资机构、园区运营方、采购方、使用方、集成商、制造商和上游材料商可能出现在同一网页。若不先确定目标产业链角色，客户名单会被大量“相关但不属于”企业污染。

### 7.7 让一次模型调用承担过多冲突任务

前序实验表明，让同一次调用同时完成证据复核、范围排除、供应角色判断、父子消歧、粒度统一、重命名和完整目录输出，容易造成保守不合并、错误合并或漏项。应拆分为有限、可校验的步骤：候选发现、主体识别、事实抽取、赛道核验、冲突消解和最终汇总。

### 7.8 允许模型静默漏项

若输出契约允许省略输入对象，就无法区分“有意排除”和“忘记输出”。批量任务必须要求每个输入对象获得唯一处置结果，例如 `match`、`not_match`、`insufficient_evidence`、`duplicate` 或 `failed`，并由程序检查数量、唯一性和引用完整性。

### 7.9 把同一模型的复核当成绝对真相

增加一次模型审核可以降低部分错误，但同一模型仍可能重复同类偏差，尤其是在父子赛道和相邻产业链角色上。高风险边界需要确定性规则、代表样本回归和人工抽查共同约束。

### 7.10 用增加数量掩盖质量问题

更多搜索词、来源或候选企业只会提高召回，不会自动提高精度。验收必须同时看有效企业率、错误角色率、证据充分率、重复率、未知率和来源覆盖，不能只看最终名单条数。

### 7.11 修改参数却复用旧缓存

赛道版本、提示词、模型、来源、时间范围、规则、阈值和解析器变化都可能改变结果。缓存键和任务输入指纹必须包含这些处理版本。未经核对就复用旧结果，会产生表面成功、实际混版的产物。

### 7.12 遇到普通故障就删除数据库或全量重跑

删除状态会丢失证据链、错误记录和已支付的 API 结果，也会使问题更难复现。正常故障应按最小失败单元恢复；只有数据库确实损坏且用户明确允许放弃历史状态时，才创建新工作目录或重建状态。

### 7.13 把运行环境问题写进业务结论

受限沙箱无网络、依赖未安装、证书异常或 API Key 权限不足，都属于运行环境问题。必须先做网络和权限前置检查；不能在受限环境中反复执行，让网络失败被持久化为业务来源失败。

### 7.14 为快速演示另写一套简化业务流程

演示、Skill 包装或便携入口可以调整安装方式、路径和编排，但不能另写一套看似相同的业务逻辑或简化看板。否则即使命令能够运行，流程、统计和最终效果也会与正式项目分叉。应复用同一生产模块、同一数据契约和同一渲染模板，并做固定响应下的结果等价测试。

### 7.15 依赖开发机器的隐式条件

不得依赖绝对路径、全局 Python 包、开发者 `.env`、本机数据库、未声明的代理或历史缓存。新工作区必须能够从清洁环境初始化，并明确要求的外部 API、Key 获取方式、数据发送范围、费用和权限。

### 7.16 在日志、命令或产物中泄露凭证和敏感数据

API Key 不得写入版本库、命令历史、测试夹具、日志和导出文件。若由 Agent 代用户配置，应通过不回显的标准输入或安全凭证接口写入本地忽略文件。企业名单及调用外部模型时发送的字段也需要遵守公司数据合规要求。

## 8. 新项目建议保留的审计数据

至少保存以下对象及版本关系：

- 赛道注册表快照；
- 发现任务、查询词、来源目录和搜索原始响应；
- 候选企业主体、别名、统一社会信用代码和去重关系；
- 页面与文档的原始引用、正文指纹和访问状态；
- 企业事实、证据摘录、来源类型及时间；
- 企业—赛道判断、产业链角色、纳入排除依据、置信度和不确定性；
- 模型、提示词、规则、Schema 和程序版本；
- 失败状态、重试记录、人工修订及修订原因；
- 最终名单的发布批次、数据范围和质量报告。

原始材料、结构化事实、模型推断和最终业务名单应分层保存。人工修改不能覆盖机器原值，应保留修改前后内容、修订人、修订时间和原因。

## 9. 首期验收建议

不要直接以全国 704 条赛道全量启动。首期应选择少量边界相对清楚、供应角色明确且公开信息较充分的赛道，建立可人工核验的代表样本。至少评估：

- 候选发现召回是否覆盖已知代表企业；
- 企业主体识别和去重是否正确；
- 供应方、使用方和关联方是否被正确区分；
- 每个纳入结论是否有直接证据；
- 父子赛道、多赛道归属和冲突规则是否一致；
- 来源失败、未知日期和证据不足是否被诚实标记；
- 相同输入和版本重跑是否稳定；
- 中断恢复是否避免重复 API 调用；
- 名单条数之外的精度、重复率、证据充分率和人工驳回率是否达到要求。

只有在代表赛道上形成稳定的数据契约、审核口径和错误分类后，才扩大赛道数、地区和来源范围。
