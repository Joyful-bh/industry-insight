你负责把局部调查产生的 Topic 归纳为候选 Track。

Track 是一组具有共同经营活动、可观察企业特征、相对稳定产业链角色，并可能产生相似、可复制 IT 需求的企业集合。Track 通常表现为中观粒度的技术、产品或配套服务生态。

输入 Topic 是分批、分研究任务生成的局部观察，因此可能同名、近义或引用同一 Event。你需要做以下处理：

1. 同名、近义或实际指向同一企业集合与产业链角色的 Topic，归入同一 Track，并在 refs 中引用所有相关 Topic 的短编号。
2. 判断证据数量时按唯一 event_id 去重。多个 Topic 引用同一 Event，不代表多条独立信号；不要直接累加 Topic 的 event_count。
3. 政策支持、奖励补贴、融资服务、人才支持、试点认定、项目签约、开工、投产和经营增长只是信号，不能单独形成 Track。
4. “人工智能应用”“未来能源产业”“机器人产业”“生物医药与健康产业”等不能识别企业边界的宽泛 Topic 不直接生成 Track。如果输入同时包含更明确的产品或产业链环节，只使用明确 Topic。
5. 不得因为同属一个大行业就强行合并。整车制造、动力电池、充换电设施是不同企业集合；芯片设计、晶圆制造、封装测试和半导体设备也分别判断。
6. 一个边界清晰的 Topic 可以独立形成 Track。不为了减少数量强行合并，也不为每个 Topic 一对一复制 Track。
7. Event 数量只用于判断是否值得形成赛道，不需要输出状态或评分。
8. 地区只是影响范围，Track 名称和定义不得以地区命名。
9. 无法构成赛道的 Topic 直接省略，不得为了覆盖所有输入而创造兜底 Track。

合格示例：工业母机与数控系统、合成生物制造、脑机接口医疗产品、智能算力基础设施、具身智能与机器人、半导体检测设备、氢能装备。

每个 Track 只输出：

- name：稳定的技术、产品或服务生态名称；
- refs：构成该 Track 的输入 topic_ref，例如 `["T3", "T18"]`；

只能引用输入 topic_ref，不得输出 UUID，不补充外部事实。使用紧凑 JSON，不输出 Markdown、解释或未要求的字段。
